# Android Knowledge V2 Architecture

## Purpose

The knowledge system should be rebuilt around one authoritative model instead of growing as a report directory plus a patch archive plus a later incoming pipeline.

The target model is:

```text
knowledge-events/        # authoritative knowledge records
evidence/ inside events  # proof, source, verification, search, and import facts
daily/ weekly/ patches/  # materialized views generated from events
index/ site/             # generated search and UI products
incoming/                # write-only contribution entry for new events
```

The server knowledge repository remains the authority. Local maintainer worktrees, member clones, plugin caches, and pending package directories are working copies or contribution staging areas only.

## Non-Goals

- Do not make local skill directories, plugin caches, or a member machine the authority.
- Do not let members write final `daily/`, `weekly/`, `patches/`, `index/`, or `site/` directories directly.
- Do not treat historical imports as verified modern evidence when the original material did not contain that evidence.
- Do not force team-specific review or coding-style rules into the neutral `android-framework-ops` plugin.

## Authority Model

`knowledge-events/` is the only durable source of truth.

Everything else is generated:

| Path | Role |
| --- | --- |
| `daily/` | Materialized report view for human browsing and old habits. |
| `weekly/` | Materialized report view for human browsing and old habits. |
| `patches/by-id/` | Materialized patch asset view for stable patch lookup. |
| `index/*.jsonl` | Generated search rows. |
| `index/knowledge.sqlite` | Generated structured search database. |
| `site/` | Generated UI. |

These generated directories should be safe to delete and rebuild from `knowledge-events/`.

`incoming/` is not an authority either. It is an append-only contribution protocol. A valid incoming package is accepted, normalized into `knowledge-events/`, and then indexed.

## Event Model

Use one event schema for historical data and new incoming data. Avoid separate `historical_*` event types unless behavior truly differs.

Prefer:

```json
{
  "schema_version": "2.0",
  "package_kind": "daily_trace",
  "channel": "light",
  "quality": "trace",
  "member": "member_alias",
  "date": "2026-05-26",
  "run_id": "20260526-210000",
  "project": "Android Framework",
  "summary": "summary",
  "source": {
    "origin": "incoming"
  },
  "reports": [],
  "patches": [],
  "evidence": [],
  "relations": [],
  "quality_claims": {}
}
```

Use `source.origin` to distinguish where the record came from:

| `source.origin` | Meaning |
| --- | --- |
| `incoming` | Generated by member-side automation and submitted through incoming. |
| `maintainer_manual` | Manually contributed by a maintainer. |
| `historical_import` | Rebuilt from historical reports, attachments, patches, or readmes. |
| `synthetic_test` | Synthetic package used for local or server protocol testing. |

Keep `package_kind` focused on the semantic kind:

| `package_kind` | Channel | Purpose |
| --- | --- | --- |
| `daily_trace` | `light` | Daily work trace and optional report. |
| `weekly_trace` | `light` | Weekly work trace and optional report. |
| `session_trace` | `light` | Codex session trace without a daily or weekly report. |
| `framework_change` | `strict` | A completed or stage-worthy Framework change with requirement and verification evidence. |
| `patch_contribution` | `strict` | A reusable or archived patch asset. |
| `reuse_decision` | `strict` | Explicit decision that a historical asset was reused, adapted, or rejected. |

## Evidence Model

Evidence is attached to events. Evidence should say what is known, how it was obtained, and what is missing.

Common evidence kinds:

| Kind | Applies To | Meaning |
| --- | --- | --- |
| `source` | all events | Generator, machine, profile, plugin version, import source, or maintainer note. |
| `codex_sessions` | daily/weekly/session traces | Source Codex sessions used to generate the report. |
| `historical_source` | historical imports | Original Excel row, weekly attachment, archive file, or old readme source. |
| `legacy_archive` | historical imports | Old zip/archive identity and extracted file list. |
| `legacy_readme` | historical patch imports | Old readme text retained as reference, not necessarily trusted as current truth. |
| `inferred_summary` | historical imports | Summary generated from patch name, subject, files, or report text. |
| `inferred_modified_files` | historical patch imports | Modified file facts parsed from a patch. |
| `patch_diff_facts` | patch-backed events | Files, classes, methods, resources, properties, logs, and other facts parsed directly from the patch diff. |
| `patch_problem_inference` | patch-backed events | Likely problem, likely solution, search keywords, and applicability inferred from patch content. |
| `risk_surface` | patch-backed events | Behavior areas and verification risks inferred from changed files, symbols, and code paths. |
| `changed_files` | new Framework packages | Changed files produced by patch-capture. |
| `search_before_change` | new Framework packages | Pre-change knowledge search terms, results, and reuse decision. |
| `verification_result` | strict events | Build, device, or equivalent verification result. |
| `device_verification` | strict events | Device behavior proof. |
| `equivalent_verification` | strict events | Accepted non-device proof with reason, coverage, and remaining risk. |
| `package_check` | strict events | Local package validation result. |

Historical import must not invent modern verification. If historical material lacks proof, record that as `historical_source`, `inferred_*`, or `legacy_*`, and keep quality below `validated`.

## Patch Content Analysis

Patch files are not opaque attachments. They are primary evidence. When metadata is missing, the migration and intake pipeline should inspect the patch content before deciding that the field is unavailable.

Patch analysis produces three classes of information:

| Class | Output | Rule |
| --- | --- | --- |
| Direct facts | `patch_diff_facts` | May populate modified files, symbols, modules, resources, properties, and log keys. |
| Inferences | `patch_problem_inference`, `risk_surface` | May populate likely problem, likely solution, keywords, applicability, and risk surface. |
| Unknowns | `limits` inside inference evidence | Must record what the patch cannot prove. |

Facts and inferences must stay separate.

Patch-derived facts can be treated as structured facts because they are visible in the diff. Patch-derived summaries, problem statements, applicability, and risks are inferences. Every inference must record:

- source patch path or patch asset ID
- basis lines or basis facts
- confidence
- limits

Example:

```json
{
  "kind": "patch_problem_inference",
  "source_patch": "patch.patch",
  "confidence": "medium",
  "inferred_problem": "Launcher launch path may leave the foreground activity without the expected window focus",
  "inferred_solution": "Adjust ActivityTaskManager and WindowManager focus update behavior around resumed activity changes",
  "inferred_keywords": [
    "Launcher",
    "focus",
    "WindowManager",
    "ActivityTaskManager"
  ],
  "basis": [
    "patch modifies ActivityTaskManagerService.java",
    "patch modifies WindowState.java",
    "diff touches resumed activity and focus update branches"
  ],
  "limits": [
    "original issue text was not found",
    "device verification evidence was not found"
  ]
}
```

For historical imports, patch content analysis is mandatory when a patch file is available. Missing title, summary, module, modified files, symbols, keywords, likely problem, likely solution, applicability, and risk surface may be inferred from patch content.

For new incoming packages, patch content analysis is used as a consistency check. If a member readme says the change is only Launcher-related but the patch touches WindowManager and PowerManager paths, the server should record a quality issue or warning instead of silently trusting the readme.

A strong inference improves search and reuse judgment. It does not upgrade an event to `validated`, does not replace build or device evidence, and does not prove that the patch shipped.

## Quality Model

Quality expresses confidence and reuse readiness. It is not a decoration.

| Quality | Meaning |
| --- | --- |
| `imported` | Historical material imported or reconstructed without modern validation evidence. |
| `trace` | Work happened; mainly useful for timeline/report context. |
| `candidate` | Useful asset exists, but verification is incomplete, indirect, or needs adaptation. |
| `validated` | PASS verification exists and quality claims include scope, risk, and rollback. |
| `released` | Validated and known to have shipped or been accepted into a release baseline. |
| `buggy` | Known-bad or failed attempt retained as learning evidence. |

Rules:

- `light` events may use `trace`, `candidate`, or `imported`.
- `strict` events may use `imported`, `candidate`, `validated`, `released`, or `buggy`.
- `validated` requires PASS verification evidence.
- Runtime behavior changes in a modified module require device verification by default.
- Equivalent verification is allowed only when device interaction is not the right proof, and must include method, reason, coverage, and remaining risk.
- Historical patch imports default to `imported`.

## Historical Migration

Historical data can and should be rebuilt into V2 events when the system is redesigned.

Inputs:

```text
historical daily rows
historical weekly rows
weekly attachment archives
patch files
old readmes
patch/readme links
patch content analysis outputs
existing normalized staging data
```

Output events:

| Historical Input | Event |
| --- | --- |
| Daily row | `daily_trace`, `source.origin=historical_import`, `quality=imported` or `trace`. |
| Weekly row | `weekly_trace`, `source.origin=historical_import`, `quality=imported` or `trace`. |
| Patch attachment | `patch_contribution`, `source.origin=historical_import`, `quality=imported`. |
| Patch with missing metadata | `patch_contribution` plus `patch_diff_facts`, `patch_problem_inference`, and `risk_surface` evidence. |
| Old readme | Evidence or patch readme source, not automatic validation proof. |

Migration requirements:

- Stable event IDs must be deterministic from original source identity, member, date, and content hash.
- Patch IDs must be stable across rebuilds.
- The migration must produce a manifest/report with counts: source rows, events, reports, patches, evidence, skipped duplicates, and errors.
- Patch content analysis must run before finalizing missing patch metadata.
- Missing title, summary, module, modified files, symbols, keywords, likely problem, likely solution, applicability, and risk surface should be inferred from the patch when possible.
- Inferred fields must remain marked as inferred and must record basis, confidence, and limits.
- Duplicate patches should be linked to the same canonical patch asset where possible, with relations recording the duplicate source.
- Existing historical counts must be reconcilable against the current baseline: reports, patches, archives, symbols, and issues.

## Materialized Views

The build pipeline generates compatibility views from `knowledge-events/`.

### Reports

`daily_trace` events with reports generate:

```text
daily/YYYYMMDD/member_alias/<title>.md
```

`weekly_trace` events with reports generate:

```text
weekly/YYYYMMDD-YYYYMMDD/member_alias/<title>.md
```

The generated report should include a small provenance block that points back to the event ID and origin.

### Patches

`patch_contribution` and `framework_change` events with patch assets generate:

```text
patches/by-id/<patch_id>/
├── patch.patch
├── readme.md
└── metadata.json
```

`metadata.json` must identify the source event, origin, quality, verification evidence, and whether the patch came from historical import or new incoming.

`metadata.json` should also expose patch analysis summaries when available: direct diff facts, inferred problem, inferred solution, inferred keywords, confidence, and limits.

### Indexes

Indexes are generated from events and materialized assets:

```text
index/report-index.jsonl
index/patch-index.jsonl
index/readme-index.jsonl
index/patch-readme-index.jsonl
index/archive-index.jsonl
index/knowledge-event-index.jsonl
index/evidence-index.jsonl
index/symbol-index.jsonl
index/issue-index.jsonl
index/knowledge.sqlite
```

The search layer should not require the user to know whether a result came from historical import or new incoming.
Search rows should include patch-derived facts and inferred keywords so old patches without good readmes can still be found by problem, module, symbol, or behavior area.

## Incoming Processing

Member automation and maintainer contributions submit only:

```text
incoming/YYYYMMDD/member_alias/run_id/
```

Server behavior:

1. Validate path, member, run ID, schema, references, and quality rules.
2. Normalize the package into `knowledge-events/`.
3. Record `server-result.json` in the incoming package.
4. Rebuild materialized views, indexes, and site.
5. Commit generated outputs with the server bot.

New Framework patch intake standard:

```text
android-framework-patch-capture
  -> .codex/patch-packages/<run-id>/
android-knowledge-intake --patch-package <package> --schema-version 2.0
```

`--patch` remains only as a legacy/manual compatibility path for old standalone patch files. It should not be the recommended path for new Framework work.

## Search Behavior

`android-knowledge-search` reads the generated index, preferring SQLite and falling back to JSONL.

Search result types:

| Type | Source |
| --- | --- |
| `event` | `knowledge-events/` normalized event records. |
| `evidence` | evidence entries attached to events. |
| `report` | materialized report rows from daily/weekly views. |
| `patch` | materialized patch assets from event patches. |
| `symbol` | modified files, properties, settings, resources, and log keys. |

Search results are evidence, not final truth. Consuming workflows must still judge applicability by comparing requirement, files, artifact, platform, quality, verification, and risk.
When a result is based on inference, the CLI and UI must show that it is inferred, its confidence, and the basis used to infer it.

## UI Information Architecture

The site should become a knowledge workbench, not a report archive.

Recommended top-level views:

| View | Purpose |
| --- | --- |
| Overview | Current state, historical/imported/new counts, quality distribution, recent incoming health. |
| Knowledge Events | Event timeline across reports, patches, Framework changes, and reuse decisions. |
| Patch Assets | Reusable patch assets, inferred problem, modified files, symbols, quality, verification, rollback. |
| Reports | Daily and weekly materialized reports for familiar browsing. |
| Evidence | Verification, search-before-change, source, import, patch analysis, and package-check evidence. |
| Members | Member timeline and contribution summaries. |
| Quality Issues | Missing readmes, imported-without-proof, validation failures, duplicate sources, stale assets. |

The UI must clearly distinguish:

```text
historical imported data
new incoming data
validated data
candidate/unverified data
direct facts versus inferred conclusions
```

## Plugin Responsibilities

`android-framework-ops` owns neutral Android Framework engineering operations:

- source access
- knowledge search
- requirement workflow
- remote build/deploy coordination
- final verification discipline
- patch capture
- knowledge intake

It must not own:

- Jinny-specific code style
- personal review preference
- project-local coding rules
- Codex workspace cleanup

Those belong in `jinny-android-practices`, project local rules, user skills, or `codex-workspace-care`.

## Rebuild Plan

Recommended order:

1. Freeze the V2 schema and quality rules in documentation.
2. Define patch content analysis outputs for facts, inferences, confidence, and limits.
3. Update `android-framework-ops` docs so new Framework patch intake prioritizes `--patch-package`.
4. Change server normalization so V2 report events materialize into `daily/` and `weekly/`.
5. Add tests for V2 daily/weekly materialization.
6. Build historical V2 migration from existing staging data, with mandatory patch analysis for available patch files.
7. Rebuild a test knowledge repository from V2 events only.
8. Compare counts and search behavior with the current baseline.
9. Redesign indexes to treat events as the authoritative source.
10. Redesign the site around events, assets, evidence, and quality.
11. Only then start real member incoming gray testing.

## Acceptance Criteria

The rebuild is acceptable when:

- A fresh repo can be generated from `knowledge-events/` into all materialized views.
- Historical reports and patches are represented as V2 events with honest `source.origin` and quality.
- Existing historical counts can be reconciled.
- New incoming daily/weekly/patch packages and historical events are searchable through the same CLI and UI.
- Historical patches with weak or missing readmes are still searchable through patch-derived facts and inferred problem keywords.
- Patch-derived inferences show basis, confidence, and limits, and never masquerade as verified facts.
- Framework patch contributions preserve search-before-change and verification evidence.
- `validated` is impossible without PASS device or accepted equivalent verification evidence.
- The site makes historical/imported/new/validated/candidate states visible.
- Member-side automation never writes final generated directories directly.

## Open Decisions

1. Whether to keep generated `daily/`, `weekly/`, and `patches/by-id/` in Git permanently, or generate them only in server worktree/site build outputs.
2. Whether imported daily/weekly should use `quality=imported` or `quality=trace`; the recommendation is `imported` when the source is historical migration and `trace` when generated by new automation.
3. Whether historical duplicate patch relations should be shown in the main patch UI or only in metadata/detail pages.
4. Whether old stable patch IDs must be preserved exactly, or whether a redirect map is enough.
